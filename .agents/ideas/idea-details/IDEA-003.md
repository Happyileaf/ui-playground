## 创意概述

做一个可直接用于生产网页的瞬时消息（Toast / Snackbar）通知系统：用户操作后在屏幕角落自动浮现轻量化反馈卡片，多条通知以立体堆叠方式排列、自动计时消失，支持操作按钮、悬停暂停、手势与键盘关闭，并配有一个真实业务场景演示区（保存成功、文件已删除可撤销、网络中断警告、同步失败等）来触发各类通知。它解决的是“操作之后缺少轻量、不打断、可感知的即时反馈”这一几乎所有 Web 应用都需要的体验问题，填补项目当前完全没有独立瞬时通知组件的空白。

## 预期展示效果

- **构图与整体风格**：
  - 页面中央/上半部为一个真实感的“设置 / 操作面板”演示区，放置若干可点击的业务操作（保存更改、删除项目、切换离线模式、模拟同步失败等），点击后从屏幕固定角落发出对应通知。
  - 屏幕右下角（窄屏自动改为顶部或底部安全区）为通知堆叠视口，通知自上而下（或按停靠角自适应）依次排列，整体克制、克制再克制，符合项目暗色精致基调（微弱色温倾向的深色中性底、细边框、柔和投影），严禁蓝紫渐变与刺眼霓虹。
  - 右上角沿用统一 Title 胶囊（本组件分类为 components，参照 HUD 规范保持品牌一致），底部可配单行操作指引胶囊。
- **主要视觉元素**：
  - 4 种语义类型：成功（success）、信息（info）、警告（warning）、错误（error），通过左侧语义色条或图标点缀区分，语义色仅作克制点缀而非大面积填色。
  - 每条通知含：语义图标（内联 SVG）、标题 + 一行正文、可选操作按钮（如“撤销”）、关闭按钮、底部细进度条（表示剩余停留时间）。
  - 多条通知的堆叠层次：后到的通知平滑顶入，相邻卡片通过位移与轻微缩放/透明度形成“堆叠纵深感”，超出最大可见数量时更早的通知优雅收敛。
- **层次、材质、光影与关键细节**：
  - 卡片采用高质感半透明深色材质 + `backdrop-filter` 毛玻璃、1px 微弱边框与柔和分层投影，营造浮于内容之上的层级感。
  - 进出场使用弹性而克制的缓动（cubic-bezier 过冲很轻，不夸张）；多条同时存在时的位置变化使用 FLIP 思路平滑过渡，避免生硬跳动。
  - 进度条在悬停暂停时同步冻结；语义图标可有极轻微的入场弹入，呼吸/闪烁只用于需要持续引起注意的警告/错误且非常微弱。
  - 长文本不撑破布局：标题单行、正文最多两行并省略，整体宽度有上下限，移动端横向留出安全边距且不遮挡关键内容。

## 动态与交互

- **触发方式**：
  - 点击演示区不同业务按钮，发出对应类型通知（含“带撤销操作”的通知，点击撤销后恢复演示状态并给出一条已撤销反馈）。
  - 支持连续快速触发，观察堆叠与最大数量管理。
- **自动消失与暂停**：每条通知按设定停留时长自动滑出；鼠标/指针悬停或键盘聚焦到通知内部时暂停倒计时（进度条冻结），移开后继续；无障碍/`prefers-reduced-motion` 下延长或依赖显式关闭，不依赖动画表达关键信息。
- **手动关闭**：关闭按钮点击、`Escape`（关闭最新/聚焦的通知）、触屏在通知上向停靠边缘方向滑动即可滑走，滑动跟手并有阈值判定与回弹。
- **堆叠管理**：新增顶入、其余平滑让位；达到最大可见条数时最早的通知优先退场；全部关闭后视口自然坍缩，不留下占位。
- **键盘与读屏**：通知容器具备合适的 ARIA live 区域语义（普通通知 `status`/`polite`，错误类 `alert`/`assertive`）；操作按钮与关闭按钮可 Tab 聚焦、焦点环可见；通知关闭后焦点不丢失（焦点原本在触发按钮上则自然停留）。
- **移动端触控**：统一 Pointer Events，触控目标不小于 44×44px，停靠位置避开浏览器手势区域，窄屏采用更贴边的通栏式布局。

## 核心亮点

1. **可直接上生产的完整通知体系**：4 种语义类型、自动消失 + 悬停暂停、操作按钮（撤销）、最大数量与堆叠管理、进度条倒计时，覆盖真实项目对 Toast/Snackbar 的绝大多数需求，而非“点击弹一行字”的玩具。
2. **FLIP 堆叠纵深感**：多条通知的让位、顶入、收敛全部平滑过渡，配合材质、投影与轻微缩放，形成立体而克制的堆叠观感，这是它区别于普通单条 toast 的关键视觉亮点。
3. **完善的可访问性**：区分 polite/assertive 的 ARIA live 语义、完整键盘操作、触屏滑动关闭、reduced-motion 适配，达到可用于严肃产品的水准。
4. **真实业务演示场景**：以“保存 / 删除撤销 / 离线 / 同步失败”等真实操作驱动通知，并让“撤销”真正回滚演示状态，组件价值与用法一目了然。

- **差异说明**：
  - 与 `notification-center` 的本质差异：后者是**持久化、需用户主动管理**的铃铛下拉中心（通知长期保留、未读计数、筛选、逐条/一键已读、手动开关），承载“可回看的消息列表”；本案例是**瞬时、自动消亡、不打断**的操作反馈（Snackbar/Toast），强调自动计时、悬停暂停、即时操作（撤销）与多条堆叠动画，交互模型、视觉表达和使用时机完全不同，二者互补而非重复。
  - 与各案例内部 toast 的本质差异：那些只是绑定在单个业务里的“一行复制/保存成功”文字，无类型体系、无堆叠、无操作按钮、无倒计时与手势/键盘管理，且不可复用；本案例交付的是一个**独立、完整、可复用的通知系统**及其 API 化用法演示。
  - 与 `modal`/`drawer` 的差异：后两者是**模态/遮挡式、强打断**的容器（遮罩、焦点陷阱、滚动锁定）；Toast 为**非模态、不打断主流程**的轻量反馈，无遮罩、不抢焦点（错误播报除外仅读屏 assertive），核心创意与交互方式不同。
  - 与在审 IDEA-001/002 的差异：form-wizard 解决多步表单录入与校验流转，view-transition-morph 解决跨视图共享元素的浏览器原生过渡；二者均不涉及“瞬时通知反馈、自动消亡与堆叠管理”，问题域与交互方式无交集。

## 实现约束（仅记录该案例必要的约束）

- 必须纯原生 HTML/CSS/ES6+，零框架、零 CDN、零运行时依赖，双击 `index.html` 即可离线完整运行。
- 通知的进出场与堆叠让位需在不依赖任何动画库的前提下实现（原生 CSS transition + 必要的 FLIP 计算）。
- 图标使用内联 SVG，不引入任何图标字体或外部图片；演示数据与状态全部本地构造。
- 若提供音效须遵守 Web Audio 手势懒激活规范；本创意不强制需要音效，可省略。
